
## **Architecture Overview**

### **Services**

1. **Service A: Job Submitter (API Gateway)**
    - Exposes /submit & /status/:id endpoints
    - Pushes jobs into Redis queue
    - Returns job ID to client
2. **Service B: Worker (Scalable)**
    - Consumes jobs from Redis queue
    - Performs **CPU-intensive operations**:
        - Example 1: Calculate primes up to 100,000
    - Saves result in Redis
    - Exposes /metrics endpoint (Prometheus format) with:
        - jobs_processed_total
        - job_processing_time_seconds
        - job_errors_total

 Note : **This is the service that gets horizontally scaled.**

1. **Service C: Stats / Aggregator**
    - Exposes /stats → returns job counts, avg time, queue length
    - Exposes /metrics for Prometheus:
        - total_jobs_submitted
        - total_jobs_completed
        - queue_length

---

## **Kubernetes Setup**

1. **Deployments**
    - Service A, B, C (Node.js)
    - Redis (Helm chart or YAML)
2. **Services**
    - A exposed via **Ingress + LoadBalancer**
    - B, C as **ClusterIP**
3. **HPA**
    - Target: **Service B**
    - Scale 2 → 10 pods when CPU > 70%
4. **Prometheus & Grafana**
    - Deploy Prometheus using Helm:

```
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install prometheus prometheus-community/kube-prometheus-stack
```

- Configure Prometheus to scrape metrics from Service B & C pods (/metrics)
- Deploy Grafana dashboards:
    - CPU & Memory usage (from k8s)
    - Custom metrics: job processing times, queue length, errors

---

## **Stress Testing**

Run load test against Service A (Ingress endpoint):

```
ab -n 5000 -c 200 http://<ingress-ip>/submit
```

Observe:

- Redis queue backlog grows
- Service B autoscaler triggers new pods
- Grafana dashboards update (CPU, job counts, queue length)
- After load, backlog drains as worker replicas increase
